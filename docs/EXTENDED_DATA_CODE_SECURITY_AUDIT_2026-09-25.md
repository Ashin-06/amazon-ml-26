### Normal and abnormal normalization fixtures

Six explicit normal fixtures passed: whitespace cleanup, French accents, leading-zero numbers, ordinals, `None`, and empty text. The nine assertions embedded in `prep.py` also passed when extracted and executed in isolation; their data-preparation loop was not executed.

These additional edge cases expose information loss:

| Synthetic input | Current behavior | Implication |
|---|---|---|

## 3. Additional confirmed code and robustness findings

Each finding distinguishes observed production data from a reproduced edge case or source-level risk. No fixes are applied.

### A1 — Invalid scores can be accepted as matches (high priority)

Current [output SQL](<D:/Amazon ML 26/code/business_entity_resolution/src/fast_er/model.py:347>) checks `p >= threshold`, without first requiring finite probabilities in [0,1]. An in-memory reproduction confirmed that DuckDB considers NaN greater than 0.675 and can select a NaN-scored candidate over a valid 0.99 candidate. NumPy/pandas reject NaN under the corresponding comparison, introducing another evaluation/export difference. Positive infinity also passes the threshold.

This behavior is documented in [DuckDB numeric types](https://www.duckdb.org/docs/current/sql/data_types/numeric). **No invalid score was found in the sampled saved predictions.** This is a missing validation guard, not evidence that existing v4 outputs contain NaNs.

Required acceptance: reject nonfinite/out-of-range scores, nonfinite/out-of-range thresholds, null keys, and duplicate pair keys before ownership or TSV publication. Keep intentional missing feature values distinct from invalid prediction probabilities. Python and SQL must agree on rejected input behavior.

### A2 — Unknown labelled targets are silently dropped (high priority)

The [training truth construction](<D:/Amazon ML 26/code/business_entity_resolution/src/fast_er/model.py:234>) and blocking diagnostics use inner joins from labels to records. A tiny in-memory fixture containing a label for a nonexistent target produced zero joined truth rows, without an integrity error. Such a reference can subsequently look like a singleton; duplicated label/record rows can also distort joins and denominators.

The earlier full audit found no unknown targets in the supplied originals. The danger concerns malformed, incomplete, or stale derived inputs, where current code lacks the older baseline's integrity gate.

Required acceptance: validate exact S1 label coverage, source prefixes, unique record/label IDs, list duplicates, every labelled target's existence, target ownership, and country compatibility before training or recall reporting. Never repair an invalid truth join by interpreting missing labels as genuine empty truth.

### A3 — Temporary cleanup does not prove directory ownership (high priority)

[`predict`](<D:/Amazon ML 26/code/business_entity_resolution/src/fast_er/model.py:320>) accepts a `tmp` path, allows it to exist, then later recursively removes that entire path at [line 331](<D:/Amazon ML 26/code/business_entity_resolution/src/fast_er/model.py:331>). There is no marker, containment check, or ownership check establishing that every file there belongs to this run. The default `tmp_fe` name is also shared by runs using the same scratch root.

This deletion was **not executed or simulated against real files**. Static control flow establishes the risk: a caller-supplied existing directory or another run's cache could be removed. Similar shared `duck_tmp` paths deserve concurrency checks.

Required acceptance: create a unique directory owned by the run, record its identity, validate resolved containment before cleanup, and remove only owned files. A preexisting directory with an unrelated sentinel must survive a future isolated cleanup test. Do not relocate or clean active runs as part of this audit.

### A4 — Archive selection is too broad for its security promise (medium priority)

The current [packager](<D:/Amazon ML 26/code/business_entity_resolution/kaggle/package_submission.py:18>) recursively accepts every file under `src`, `kaggle`, `configs`, and `tests`, except bytecode-cache directories. Testing its path predicate without creating files showed it would select hypothetical `src/.env`, `src/kaggle.json`, and `src/unrelated.parquet`.

Its actual current selection contains **35 files**, with no sensitive filenames, symlinks, or resolved paths outside the package root. No existing secret leak was found. The defect is that adding an unrelated/sensitive file inside one of those directories would silently widen the archive.

Required acceptance: explicit permitted files/extensions plus sensitive-name exclusions, resolved-path containment, and symlink policy. Validate the final archive manifest. Also sanitize the team-derived archive name and avoid silently overwriting an existing archive with ZIP mode `w`.

### A5 — SQL paths containing apostrophes break parsing (medium priority)

[Database setup](<D:/Amazon ML 26/code/business_entity_resolution/src/fast_er/model.py:144>) and other functions interpolate paths/settings inside SQL string literals. A benign `O'Brien` directory name reproduced a `ParserException` using the same literal construction, without accessing any file. If those settings ever become untrusted input, interpolation also enlarges the SQL injection surface.

Business names and addresses are currently read as table data; this finding does **not** show that a business name can execute SQL. The current workspace path itself has no apostrophe.

Required acceptance: parameterize paths where supported, otherwise apply correct SQL literal escaping and typed validation. Reject unintended path traversal and invalid settings. Test apostrophes, spaces, Unicode paths, and escaped separators in an isolated fixture.

### A6 — Invalid configuration can fail late or create empty evaluation groups (medium priority)

The stage drivers mostly accept raw integer/string arguments without a preflight contract. A hold modulus of zero returns a null SQL predicate; a modulus of one reserves every reference for hold. Zero chunks creates no processing loop; tiny training samples can leave one A/B half empty. `macro_f05({}, {}, [])` reproduced a `ZeroDivisionError`.

Required acceptance: validate positive chunk/worker/thread counts, meaningful split parameters, valid sample sizes, feature schemas, class availability, nonempty evaluation groups, and resource limits before expensive preparation. Invalid inputs should produce a clear early error, not silent success or a later model exception.

### A7 — The old baseline no longer has a complete installation contract (medium priority)

Current `requirements.txt` specifies the fast pipeline. LightGBM pulls SciPy transitively, but scikit-learn is not in the mandatory dependency closure. The older [baseline trainer](<D:/Amazon ML 26/code/business_entity_resolution/src/business_er/train.py:200>) unconditionally requests the installed scikit-learn version when recording its environment.

A clean installation of only current requirements is therefore not guaranteed to support the old baseline/runbook/tests. The present machine happens to have scikit-learn installed, masking this gap.

Required acceptance: clearly separate supported baseline and fast-pipeline environments, or include all dependencies required by the advertised commands. Reproduce the selected route in a clean isolated environment rather than relying on global packages.

### A8 — README's validator command points to a missing file (medium priority)

The [README command](<D:/Amazon ML 26/code/business_entity_resolution/README.md:38>) runs `python utils/validate_submission.py` from the package directory. That file does not exist there, and the current packager does not include it. The supplied validator exists elsewhere in the original resource directory.

Required acceptance: instructions must reference the actual supplied validator location, or bundle the unchanged validator in an explicitly documented location if permitted. Verify commands from the directory the README specifies. The broader stale-doc and selected-model packaging issues remain in the first review.

### A9 — Existing inline assertions do not run in the normal stage driver

The nine normalization assertions sit under [`prep.py`'s main guard](<D:/Amazon ML 26/code/business_entity_resolution/src/fast_er/prep.py:174>). `run_stage1.py` imports `prepare`, so normal stage execution skips those assertions. Python optimization can also remove assertions. Passing them here is useful but does not make them a pipeline validation gate.

Required acceptance: put behavior checks in a real `fast_er` regression suite and use explicit exceptions for runtime input guarantees. Existing tests still target `business_er`; no test-file content referencing `fast_er` was found in the prior review.

- Test `scores.parquet`: 10,240 rows; no nonfinite/out-of-range `p1` or `p`.

Training still optimizes pairwise binary log loss, while selection uses per-reference F0.5. More trees, a lower training loss, or high feature importance does not by itself demonstrate better unseen-data F0.5. Keep the earlier recommendations for a separate tune/final-hold split, identical global ownership decisions, realistic distractors, subgroup metrics, and paired model comparisons.

**Shared environment:** the global dependency consistency check failed because other installed applications require incompatible versions. Examples include TensorFlow requiring NumPy below 2.2, sentence-transformers requiring a newer transformers than installed, and a pydantic/pydantic-core mismatch. These are real environment conflicts, but they do not prove that the current LightGBM pipeline is failing. Do not repair the whole global environment during an active run. Use a separate pinned environment for reproducibility and any future neural experiment.

A passing compile/import check does not catch incompatible cached features, insufficient memory/disk, missing remote wheels, invalid data, or output-writer failures. Those are runtime and artifact-contract issues. Recorded Kaggle dependency differences and past memory failures remain relevant.

## 6. Security findings and limits

### Local source and packaging observations

- Inspected 55 tracked filenames and scanned 52 eligible tracked text files, each at most 2 MB, for recognizable Kaggle/AWS/GitHub token patterns, private-key blocks, and literal secret assignments. No matches were found. Secret values were never printed.
- No sensitive credential filenames were tracked. The workspace's credential files were not opened, used, uploaded, or enumerated into the report. Git history, ignored files, arbitrary encodings, cloud permissions, and token validity are outside this scan.
- Current prospective package selection has no sensitive filenames or external-resolving links, but its permissive directory rule remains a concrete future leak risk (A4).
- The inspected Kaggle builder uses subprocess argument lists rather than `shell=True`. That avoids automatic shell parsing for these commands, consistent with [Python's subprocess documentation](https://docs.python.org/3/library/subprocess.html#security-considerations). SQL interpolation and the separate shell helper still need their own input validation.
- The fast pipeline loads LightGBM text models, JSON, Parquet, and NumPy arrays. No pickle/joblib loading or `allow_pickle=True` was found in this source path. This is a favorable boundary, not proof that arbitrary untrusted files are safe to parse.
- All nine saved kernel metadata files specify `is_private: true`, CPU execution, and one dataset attachment. They do not verify live Kaggle dataset visibility, account authorization, or access controls. No account was contacted.

### Targeted vulnerability research
